# Yakou online integration analysis

This describes the boundary at server main `dd8eb17` (PR #25). Yakou is an opt-in development prototype, not the existing GameCore or HyakkiYagyo online mode. The server must run with `--yakou-prototype on`; it uses the first authored Yakou prototype deck for both seats and does not accept a player deck. The room ID is an invite capability and the resume token is a bearer secret. Do not log either token or expose it to the other player.

## Existing client

`ClientApp` persists across scene changes and owns `MultiplayerDebugScreen`, which owns `WebSocketTransport`. The transport has background WebSocket tasks and main-thread message queues. `ConnectionScenePresenter` establishes a connection and requests the legacy deck catalog; `LobbyScenePresenter` starts the legacy matchmaking flow. `BattlePresenter` listens for GameCore events and `StateSnapshot`, maintains presentation batches and delegates interaction to `GameplayInputCoordinator` and the selection views. These are reusable transport and visual components, but their current coordinator, action choices, animations, phase buttons and `StateView` encode GameCore assumptions. They cannot determine Yakou legality or be reused as an authority.

## Server contract

Yakou uses protocol version 2 envelopes on the same listener, with separate `YakouCreate`, `YakouJoin`, `YakouResume`, `YakouCommand`, `YakouSnapshot` and `YakouLeave` messages. Create/join bind a server seat and supply a resume token; resume rotates it. Every successful command produces a `YakouCommandResult` followed by viewer-specific snapshots. The monotonically increasing sequence belongs to the Yakou session. Repeating the same request ID and command returns the cached result without broadcasting another snapshot. Requesting a snapshot after such a retry is necessary when the client has not received the resulting state. Leave closes the room for both seats. A disconnect alone preserves the room until expiration.

The snapshot has `Phase`, `ActivePlayerId`, `PriorityPlayerId`, `TurnNumber`, `WinnerPlayerId`, `Players` and `Attacks`. Each player has life, ki, counts, five `FieldSlots`, public graveyard and exile; only the viewer's hand is populated. The owner's `SummonChoices` include method, source zone, material candidates, required count and available slots. `PendingSelection` is present only for its owner and includes server-provided candidates when `Status` is `Ready`; `Unavailable` is explicitly unresolved. Snapshots do not include opponent hand or deck order. Card definition IDs must be resolved through `CardLibrary.LoadYakouResources`, not the similarly numbered legacy catalog.

The gateway accepts `StartTurn`, `Summon`, `ActivateMainSpell`, `ChooseEffect`, `Manifest`, `Postpone`, `Redraw`, `BeginRaid`, `AssignBlockers`, `RespondWithRaidShield`, `RespondWithRaidTactic`, `PassRaidResponse`, `ResolveRaid`, `BeginSpellResponse`, `RespondWithNegation`, and `PassSpellResponse`. Only the server validates costs, targets, priority, resolution and card movement. Some authored effects remain unsupported; see server `YakouEffectCoverage.md` and `YakouV03Migration.md`.

## Development client and remaining work

In an Editor or Development Build, select the Local environment and connect to a server launched with `--yakou-prototype on`. The lobby has a **Yakou prototype** button. Create a room and privately share its room ID, or enter that ID and join. Both players use the server's fixed prototype deck. The separate development screen displays each received viewer snapshot, the Yakou catalog's card descriptions, summon choices, targets, costs, field slots, and attack assignments. Buttons send gateway commands; the server decides whether an action is legal. Available effect targets come from `PendingSelection`. The screen exposes raw instance IDs for prototype actions and does not replace the designed GameCore BattleScene.

`MultiplayerDebugScreen` routes Yakou messages through `YakouSessionClient` on the existing WebSocket. Requests are correlated, commands wait for server results and snapshots, and an uncertain command is retried with its original request ID after reconnect. Resume credentials remain in memory and are cleared when the server endpoint or account is changed. The server rotates a resume token on successful resume; losing the resume response can make that old token unusable. If creation or join response is lost, the client cannot recover a token it never received. Closed or expired rooms cannot be resumed; the disconnected room can be forgotten locally. A client should not publish room IDs or tokens.

The development interface deliberately avoids guessing availability: the server can reject actions, and unsupported effect selections show `Unavailable`. It offers all gateway command shapes but does not yet provide the scene-authored BattleScene's card visuals, drag gestures, animations or polished target/cost interactions. It has not been validated with two separately launched Unity players or for every authored effect and command. Unity PlayMode integration tests use two real Unity WebSocket transport components and an opt-in server; they are not a substitute for a two-window UI test. Runtime card effect coverage remains incomplete on the server.
